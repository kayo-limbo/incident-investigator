# 固定协议的新参数验收记录

2026-10-23，使用此前已实现的调查协议采集五组新参数下的请求。没有调整调查代码、提示词或 Schema。参数和代码指纹在采集前记录，详细方法见 [固定协议验收](../decisions/009-fixed-protocol-evaluation.md)。

每组 18 次负载请求，另有一次预热，共采集 95 条窗口请求；以下统计不含预热。五组均通过独立业务/span 检查和离线规则验收。结束后恢复默认连接池、正确库存地址及零延迟，订单业务响应检查通过。

正常库存池超时说明 PoolTimeout 不必以库存处理变慢为前提；小池低负载说明连接池上限小也不必然造成异常。成功请求发送前耗时低不能排除失败请求发生池超时。以上都是该实验条件下的观测，不直接推出生产环境的唯一根因。

新增 5 项测试，全量 88 项通过。测试覆盖场景未实际出现、采集或恢复不完整、计划/协议变化、失败轮继续保留、已存在输出拒绝，以及采集失败后的恢复尝试。

### 失败分析

- 普通 ReAct 两次均正常结束，文字解释也指出无异常或池超时，但 `finding.code` 错填 `inventory_latency`。引用合法和 termination=completed 不足以判为成功，独立类别检查将其拒绝。
- 假设策略一次输出 Schema 不接受的 `finish.type` 字段，整个动作被拒绝；两次结论引用未全部关联所选假设。第一轮池超时案例中，候选引用了未关联的池配置字段及另一观测中的在途数；同名字段不能替代具体 trace/span 字段。
- 另两次为适配器 `invalid_response`。既有适配器将多种响应或解析问题合并记录，没有保留原始响应，无法进一步归因为某种 JSON 语法错误，也不能称为合理拒答。
- 假设策略五个未通过的报告均为执行或校验失败，没有被计作“证据不足时正确拒答”。本轮不修改协议补救，也不按被拒绝候选的正确类别回填成功率。

### 用量与解释边界

| 策略 | 通过 / 调查次数 | 模型调用 | 工具调用（含摘要） | 总 token | 总耗时 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 规则 | 10 / 10 | 0 | 32 | 0 | 31 |
| 普通 ReAct | 8 / 10 | 49 | 49 | 257662 | 95001 |
| 假设策略 | 5 / 10 | 23 | 23 | 134724 | 79095 |

用量包括失败调用，本次没有缺失 token 用量。ReAct 有两次重复下钻，假设策略没有；这些数量不足以证明去重策略的效果。假设策略多次提前失败，其较低调用和 token 总量不能直接解释为效率提升。两种策略的提示和状态结构不同，模型服务的别名也不等于固定权重版本。

人工抽查了五份通过的假设报告。共同作用场景同时查看成功与失败请求；小池低负载没有仅凭池上限小误报。仍存在“P95最高trace”“池竞争不成立”等不够严谨的措辞，且个别报告把池等待与发送前计时范围混用；自动结构校验没有证明这些语义正确。

两轮执行均完整结束，退出码为 1 表示存在未通过案例，不表示整个回放中断。回放后重新校验 30 份报告的独立判分、同快照输入和当前代码指纹，结果与原记录一致。[机器可读记录](holdout-results.json) 保存每次结果、错误分类和用量；完整报告留在被 Git 忽略的本地文件中。

这些是同拓扑、已知故障机制的新参数样本，不是未知故障泛化测试。两轮回放共享快照，不视为两次独立环境采样。当前结果不支持宣称假设策略更可靠；下一开发轮应优先区分解析错误、Schema 错误和证据关联错误，评估预算内的有限纠错，再使用新的验收样本。当前五组结果必须保留，后续调参不能重算为本轮通过。
