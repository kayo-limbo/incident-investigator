# 双窗口订单开发场景

2026-11-07。实现 [任务设计030](../decisions/030-cross-source-investigation-tasks.md) 的首个采集里程碑：双窗口冻结、只读查询、来源消融、有界开环驱动与离线重建。没有接入模型策略、Worker或多Agent；这些开发场景不构成独立测试集。

## 实现与使用

- `lab/orders/runtime_observation.py`：新增 `/observations/client/timed`，提供进程单调微秒；原接口字段不变，旧bundle严格Schema仍可读取。
- `backend/investigation/paired_evidence.py`：独立schema 3 / paired-bundle-v1；窗口内部进程/配置稳定、计数守恒、排空、时钟及来源时间对齐校验。跨窗口允许重启，但不能跨进程相减计数。
- `evals/collect_paired_windows.py`：开发采集和离线audit入口；原始控制/业务记录与Agent证据包分开保存，按来源白名单投影。

在项目根目录运行，需要本地Docker服务：

```powershell
docker compose build orders inventory
.\.venv\Scripts\python.exe -m evals.collect_paired_windows collect .snapshots/paired-new-run
.\.venv\Scripts\python.exe -m evals.collect_paired_windows audit .snapshots/paired-new-run
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_paired*.py" -v
```

采集目录必须不存在。默认五类各两次、每窗发送15秒；可用 `--cases stable downstream`、`--repeats 1`、`--duration 15` 限定开发采集。目录中的计划固定参数、源码hash和来源归档；更改实现后不得继续旧计划，离线audit也会拒绝代码指纹不一致。复现旧轮次需使用对应源码归档，不能用新准入逻辑回填历史成绩。

每次尝试先预热三次，再记录before、开环发压、排空、记录after；预热不计入窗口。驱动使用perf_counter与截止时间复查，等待前一次响应不会阻止下一次预定发送。最多1000请求、在途100、单请求5秒、排空10秒、调度落后100ms、尾部占发送时长20%、运行区间额外耗时25%。达到限制即记录无效，不通过增大上限掩盖过载。

Trace按trace_id的SHA-256排序选前40条，固定算法不依赖状态、延迟或故障类别。原有配置字段保留；告警是完整驱动响应的client P95，Trace统计是样本内服务端耗时，不能混用。运行速率用实际服务端单调区间和计数计算，包含尾部与观测开销，不等于精确发送区间的入口速率，也不等于并发。

Trace查询区间采用服务端before/after墙钟时间，与订单根span处于同一时钟域；驱动宿主机时间只用于自身记录，不与容器时间作严格大小排序。仍拒绝服务端墙钟/单调间隔异常、根span越界及窗口内重启。

每个有效采集单元另存Trace-only、runtime-only证据包；缺失来源没有原包ID或控制端链接。`PairedSession`初始告警计一次工具调用，四种(window, source)组合最多各查一次，完整读取共5次；默认总预算6。引用绑定快照、窗口、来源、字段，未查询来源不可引用。该接口目前供离线检查，尚未接入模型动作协议。

## 开发过程与失败记录

第一轮 `.snapshots/paired-20261107-dev1`：10次尝试、5次采集有效，最后恢复成功。以下失败保留，没有补改旧报告：

- 一个稳定窗口被严格时间下限拒收：服务端单调间隔14.989840秒，驱动墙钟14.983465秒，事件循环时钟却认为15秒已结束。改用perf_counter并在sleep返回后复查deadline；未放宽15秒下限。Windows计时粒度与现象一致，未做操作系统级根因证明。
- 两个容量变化窗口在20次/秒、池1时出现4.8–5秒排空尾部，超过20%限制。
- 两个入口变化窗口在40次/秒、池2时达到100在途上限，未完成预定发送。

第二轮开发参数：稳定及重启为60ms/池2/10次每秒；下游为池6/10次每秒，60→350ms；容量为60ms/17次每秒，池2→1；入口为60ms/池2，20→33次每秒。所有池等待配置1000ms。参数调整属于开发集校准，不作为未知参数泛化成绩。

第二轮 `.snapshots/paired-20261107-dev2`：10次尝试、9次采集有效、7次任务准入通过，独立业务与配置恢复成功；该轮冻结源码下audit重算一致。一次重启场景因清单原子替换遇到Windows PermissionError而失败，期间清单正在被读取；随后增加最多6次原子替换尝试、累计300ms退避，持续失败仍抛错，原目标文件不截断。修改后另建重启复验，不覆盖或补写该轮失败；当前源码audit会拒绝该轮旧指纹。

两次容量变化成功形成慢请求，但运行区间包括排空尾部，相同发送节奏下得到区间速率比0.896和0.887，低于0.9门槛。因此不能说“流量保持不变已由观测证明”，也不放宽门槛使样本通过。下一步需要把发送区间结束读数与最终排空读数分开，再验证固定区间入口计数；不是继续加大负载或立即接模型。

写入修复后的 `.snapshots/paired-20261107-io-fix` 两次重启复验有1次有效，另一次被跨时钟对齐拒收：host start比server before早229微秒。由此修改Trace区间为服务端时间，而不是放宽对齐阈值；此前宿主机时间驱动的失败样本仍保留，恢复通过。这些轮次是逐步调试记录，不能将其中成功样本拼成一组正式基准成绩。

最终 `.snapshots/paired-20261107-clock-fix` 以当前源码采集两次重启对照：2/2采集有效且任务准入通过，audit输出valid=2、attempted=2、task_ready=2、recovery=true。当前命令可直接离线重算这一轮。五类全套当前源码的正式对照尚未开展，容量任务仍待修正观测口径。

每轮 `collection.private.json` 区分 `valid`（采集完整性）与 `feasibility.ready`（目标症状和控制条件是否形成）。后者是开发准入规则：参考业务P95<150ms且无失败、库存样本P95<150ms、发送前样本P95<50ms；下游事件库存/业务P95≥250ms；容量和入口事件发送前P95≥150ms且库存<150ms、业务P95至少增加100ms。非入口场景区间速率比需在0.9–1.1，入口场景至少1.5。规则不是通用诊断阈值，也没有交给Agent充当真值。

## 验收边界

离线audit从原始业务响应、计数和抽样原始span重建证据包与来源消融，复算可判别性摘要，核对计划、归档、采集成员和恢复观测。失败尝试单列保留；采集成功不自动等于解释正确。每个有效包的因果可判别性仍需人工审查，`source_review` 保持 `manual_review_required`，不能把此字段当作已完成语义评分。

正式模型实验之前仍需冻结策略、阈值及独立测试参数，再采新的测试单元。单纯看到池配置变化即可解决的样本须保留为单源可解对照；不要求所有问题都使用两种来源。第二套拓扑和多Agent继续后置。本轮无模型调用费用。

## 来源可判别性复核

对第二轮9个有效采集单元的完整、Trace-only、runtime-only共27份视图进行真实离线查询检查，每份完整读取均5次工具调用，不访问网络。结合原始业务和样本统计逐类复核：

| 问题 | Trace单源能支持什么 | runtime增加什么 | 当前限制 |
| --- | --- | --- | --- |
| 样本下游变慢 | 参考/事件库存耗时上升，可单源定位 | 配置和区间入口变化对照 | 仍非唯一因果证明 |
| 容量下降 | Trace已含池2→1，且发送前升高，保留为强单源对照 | 进程变化、累计计数与区间速率 | 尾部使速率变化控制未通过，不能宣称排除入口因素 |
| 入口变化 | 看到池配置不变、库存稳定、发送前升高 | 两个完整计数区间的速率增幅 | 只能说该区间入口速率上升；不能由样本条数推出全体速率 |
| 稳定/重启对照 | 样本阶段未退化 | 进程身份变化与计数边界 | 单源正常样本不能保证整个系统无异常 |

runtime单源不包含库存耗时或发送前阶段信息，无法独立定位慢阶段。以上是任务证据边界的人工复核，尚非策略对照或语义验证器成绩；机器报告中的manual_review_required保持原始值，本节不回写冻结报告。
