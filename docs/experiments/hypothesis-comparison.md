## 相同条件与计分

两种模型策略均使用 `deepseek-flash`、非思考 JSON 模式、单次输出上限 2048 tokens、网络阶段超时 30 秒；每场景最多 6 次工具调用（摘要算一次）和 6 次模型调用。相同冻结快照通过同一只读会话提供，场景标签只在评测器中使用。完整模型报告和快照为本地产物，未纳入 Git。

通过须同时满足 completed、类别符合独立标签、引用来自绑定快照的已下钻字段。假设策略另检查版本顺序、证据可见时序、查询与证据对应关系，以及最终引用和假设的关联。工具调用成功、模型称成功或错误结束后的 insufficient_evidence 都不能单独算通过。

## 四轮结果及失败

| 轮次 | 规则 | 普通 ReAct | 假设策略 | 本轮观察 |
| --- | --- | --- | --- | --- |
| r1 | 4/4 | 4/4 | 0/4 | 一次模型响应错误、两次动作 Schema 错误、一次结论引用关联失败 |
| r2 | 4/4 | 4/4 | 0/4 | 两次模型响应错误、一次复制只读 version 字段、一次类别与文字解释不一致 |
| r3 | 4/4 | 3/4 | 2/4 | 正常和慢库存通过；小池响应错误，联合场景仍复制 version |
| r4 | 4/4 | 3/4 | 4/4 | 版本维护移交执行器后，四场景通过；普通 ReAct 正常场景引用了不存在的标签 |

r1 的结论关联规则只允许直接支持最终原因的字段，无法自然表达“用反证排除另一个解释”。r2 改为允许最终决策同时关联 supported/refuted 假设，并要求字段归属明确。小池场景虽然描述了库存 P95 正常，却选了库存慢的联合类别，独立评测判为失败。

r2 加入安全的错误位置与类型记录，首次明确观察到 `version:extra_forbidden`；r1 未保留 Schema 错误位置，不能事后认定也是同一错误。`invalid_response` 是既有适配器的合并错误码，未保留原始响应，无法进一步判定为哪种响应或 JSON 解析问题。

r3 精简提示与上下文、澄清类别选择，但只读版本复制仍复发。r4 将版本管理完全交给执行器：模型只提出假设内容，执行器用决策前的版本填入 expected_version、校验并追加历史，查询与最终版本关系由程序生成。仍严格拒绝未知字段，没有默默修补模型动作。

## 最终结论抽查

- 正常场景：两类异常假设从 open 更新为 refuted；引用库存耗时和发送前耗时。模型说“最高 P95 trace”并不严谨，P95 是窗口统计量，不是单条 trace 的属性。
- 小池等待：保留发送前等待解释，反驳库存慢；最终同时引用约 565 ms 发送前耗时与约 82 ms 库存耗时，说明池竞争仍属推断，没有把小池配置本身认定为根因。
- 慢库存：库存慢 supported，发送前等待 refuted；引用约 502 ms 库存 span。模型使用“池等待不成立”偏强，当前证据仅支持未观察到超过阈值的发送前等待或 PoolTimeout。
- 联合场景：保留两个 supported 假设，分别引用成功请求的库存耗时和失败请求的 PoolTimeout；没有用成功请求很低的发送前耗时抹去失败样本。

程序未自动发现上述措辞问题。结构校验保证可追溯与一致性，不证明语义支持或唯一根因；当前结果仍需要抽查。

## 复现

```powershell

.\.venv\Scripts\python.exe -m evals.run_hypothesis_comparison --replay docs/experiments/window-comparison-final.private.json --output docs/experiments/hypothesis-comparison-new.private.json
```
