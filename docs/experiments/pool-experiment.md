# HTTP 连接池竞争对照实验

## 条件与运行

2026-10-17 在本地 Docker Compose 运行 orders → inventory，HTTPX 0.28.1 / httpcore 1.0.9，HTTP/1.1。每组预热 1 请求，随后采集 24 请求，按指定并发度分批突发。普通库存工作负载统一为 80 ms 异步模拟处理，慢下游为 500 ms。连接池等待超时均配置为 250 ms；这不是端到端截止时间。

```powershell
docker compose build
.\.venv\Scripts\python.exe -m lab.run_pool_experiment
```

脚本采集所有 168 个请求的实际 Jaeger 链路，校验父子关系、状态、CLIENT 观测字段；PoolTimeout 请求必须尚未开始发送请求头且没有库存 SERVER span。结果包含故障真值，保存在 `pool-results.json`，不得直接供调查 Agent 读取。

## 实测结果

以下各 P95 独立计算，不能将不同列相减后解释为同一个请求的排队时间。库存耗时与发送前耗时仅统计有对应观测的成功请求；池超时请求未发出，没有这些观测，必须同时看失败数量。

| 条件 | 库存模拟处理 ms | 池上限 | 并发 | 成功/请求数 | PoolTimeout | 订单 P95 ms | 库存 P95 ms | 成功请求发送前 P95 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 健康 | 80 | 4 | 8 | 24/24 | 0 | 175.0 | 81.9 | 89.4 |
| 健康宽池 | 80 | 8 | 8 | 24/24 | 0 | 95.8 | 82.1 | 5.1 |
| 下游慢 | 500 | 8 | 8 | 24/24 | 0 | 512.7 | 502.7 | 7.0 |
| 小连接池 | 80 | 1 | 8 | 24/24 | 0 | 659.2 | 82.7 | 572.4 |
| 下游慢引发池竞争 | 500 | 4 | 8 | 12/24 | 12 | 514.1 | 502.2 | 9.3 |
| 小池低负载 | 80 | 1 | 1 | 24/24 | 0 | 87.8 | 82.3 | 0.6 |
| 恢复健康条件 | 80 | 4 | 8 | 24/24 | 0 | 173.9 | 82.0 | 89.0 |

全部七组通过验收。实验最终额外恢复零延迟、正确库存地址、池上限 100、池等待超时 2000 ms，订单业务探针通过。

## 可以得出的结论

- 同为订单变慢，宽池慢下游主要耗时在库存内部，小池正常下游主要耗时发生在订单发送前。对照干预支持小池在该并发负载下形成瓶颈，但 pre_send 仍不是单独测得的纯 pool wait。
- 健康池 4/并发 8 已有轻度发送前等待，却没有错误；存在等待本身不等于故障。当前没有定义生产 SLO。
- 保持池 4/并发 8，只增加库存处理时间，即可从全部成功变为半数池超时。因此 PoolTimeout 说明等不到连接，不能单凭它判定池配置过小。
- 保持池 1，降低到串行负载后全部成功且发送前耗时很低。因此不能只读池配置值就判定根因。
- 混合场景中成功请求发送前耗时很低，同时有大量未发送的失败请求。只分析成功链路会漏掉连接池竞争，后续调查需要窗口内多请求证据。

## 首次失败与修正

首次实验错误地要求小池组必须出现 PoolTimeout。实际 24 请求全成功，库存 P95 约 82 ms，发送前 P95 约 562 ms，说明已产生明显等待但没有超时。检查固定版本 httpcore 的连接分配循环，发现请求可在连接暂不可用后重新等待，单次 pool timeout 不能视为累计发送前等待上限。

因此修正小池组验收为“库存处理正常且成功请求发送前延迟明显”，仍保留混合场景必须出现真实 PoolTimeout 的检查。没有为了满足预期而扩大或伪造异常。失败运行也经过 finally 恢复服务，原始记录保留于被 Git 忽略的 `pool-initial.private.json`。

## 验证范围与限制

45 项本地测试通过，新增真实 TCP 连接池测试验证超时请求未发送、成功等待观测、取消后资源恢复及非法配置。容器镜像重建后完成上述七组验收。

本实验没有调用模型，不是 Agent 与规则的新场景对比。当前调查工具仍只投影旧字段、仍接受单 Trace 输入；下一步需要提供受限窗口查询、池配置/并发观测和候选假设，再公平扩展规则基线与 Agent。单次小样本突发负载也不能代表生产到达率、吞吐或泛化准确率。

字段定义及官方来源见 [连接池观测设计](../decisions/005-pool-contention.md)。
