# 库存延迟实验

在 Docker Compose 环境中，每组预热 1 次，再串行请求 10 次，并发为 1，商品为 demo。三组均返回 HTTP 200、can_order=true；30 次请求均匹配到库存处理、订单下游调用、订单处理三条日志。

本次实测中位数（毫秒）：

| 场景 | 注入延迟 | 客户端 | 库存处理 | 订单等待库存 | 订单处理 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 正常 | 0 | 5.030 | 0.318 | 2.025 | 2.384 |
| 变慢 | 500 | 509.798 | 501.570 | 505.066 | 505.721 |
| 恢复 | 0 | 3.615 | 0.246 | 1.597 | 1.882 |

注入后库存处理耗时增加约 501 ms，订单等待库存的耗时也相应增加，支持“订单变慢主要来自库存请求”的解释。移除延迟后，三处耗时均回到毫秒量级。各项耗时是包含关系，不能相加。

这是一轮小规模功能实验，不是吞吐能力测试或统计显著性结论。这里的库存内部原因由人工注入已知；仅凭计时日志不能进一步区分真实环境中的数据库等待、网络等待等根因。

原始样本及请求 ID 见 `delay-results.json`，其中时间戳使用 UTC。复现：先 `docker compose up --build -d --wait`，再运行 `.\.venv\Scripts\python.exe -m lab.run_delay_experiment`。重新运行会覆盖 JSON，表格是本次运行记录，不会自动更新。

实验结束已恢复 INVENTORY_DELAY_MS=0。控制参数和包含真值的实验文件未来需与诊断 Agent 的可见数据分开。
