# 第二类故障：订单配置了错误的库存端口

2026-10-15 实测。复现入口：`.\.venv\Scripts\python.exe -m lab.run_config_experiment`。每组 3 次串行订单请求，组间通过 Compose 重建订单容器以更新配置，库存始终保持运行且注入延迟为 0。

| 阶段 | 订单配置目标 | 订单请求 | 订单 SERVER 中位数 | 订单容器内直接探测正确库存地址 |
| --- | --- | --- | ---: | --- |
| 正常 | inventory:8001 | 3/3 HTTP 200 | 4.768 ms | HTTP 200，库存 10 |
| 错误端口 | inventory:8002 | 3/3 HTTP 503 | 4.332 ms | HTTP 200，库存 10 |
| 恢复 | inventory:8001 | 3/3 HTTP 200 | 5.085 ms | HTTP 200，库存 10 |

实验读取订单容器内实际的 INVENTORY_BASE_URL，确认配置生效；从 Jaeger 查询每次请求的实际 span 并检查父子关系、HTTP 状态及错误标记。故障阶段只有两个订单 span，CLIENT span 记录 `server.address=inventory`、`server.port=8002`、`error.type=ConnectError`。

这些证据说明本次请求没有进入库存应用；订单容器仍能访问正确地址，所以不能把 503 解释成库存宕机。结合正确服务端口与实际配置，支持定位为订单侧库存端口配置错误。不能单凭缺少 span 作出同样判断，因为采样、遥测丢失或其他网络问题也可能产生不完整链路。

与延迟故障的区别：延迟场景请求进入库存，出现长耗时库存 SERVER span；本次错误端口产生连接错误，且正确地址探针正常。连接错误不保证总是快速失败，因此不依赖耗时阈值判定故障类型。

实验结束已恢复 `http://inventory:8001`，恢复阶段连续 3 次业务请求成功。原始链路和独立探针结果保存在 [config-results.json](config-results.json)。这是小规模功能验收，不能作为性能统计结论。

场景名称、预设错误地址、评分与恢复逻辑只属于实验控制层；未来调查工具可以读取实际目标和观测证据，但不能读取这份包含真值的实验记录来推断答案。
