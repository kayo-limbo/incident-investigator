# Agent 能力演进路线（讨论稿）

本文件是后续里程碑建议，不代表这些能力已经实现。目标是可恢复、基于证据的故障调查与受控处置：Agent选择调查方向、检验竞争假设、处理证据冲突，在预算内给出可追溯结论或拒答。

## 现状与优先级

已有只读证据工具、冻结快照、假设账本、预算/取消、规则基线、独立评测、持久化任务、租约Worker和状态SSE。任务接管仍会重新调查，不是步骤级恢复。2026-10-25的五组快照两轮回放中，普通ReAct为8/10、假设策略为5/10；格式与证据关联失败需要优先解释。结果来自有限的已知机制样本，不能泛化为模型能力排名。

LangGraph承担节点调度、条件跳转、检查点与中断；领域代码继续承担证据引用、工具权限、预算规则、审批授权、处置幂等和独立验收。图节点不是天然的Agent；只有具备局部目标、上下文、工具选择与多轮决策的执行单元才作为子Agent讨论。

## 里程碑

| 阶段 | 具体交付 | 验收后才可声明的能力 |
| --- | --- | --- |
| 1. 单Agent图编排 | 迁移假设策略，拆决策/校验/接纳/查询/结束节点，共享既有领域逻辑；记录状态schema版本 | 图实际控制多轮调查；脚本化动作下的预算、引用、拒答、取消与旧行为对照通过 |
| 2. 调查质量与场景 | 细分模型/格式/引用错误，加入预算内有限协议纠错；增加分散证据、无关变更与缺失数据场景 | 能明确区分执行失败、合理拒答和误判；修正效果由新留出样本验证 |
| 3. 持久化图恢复 | PostgreSQL检查点、显式可序列化状态、恢复时累计用量、Worker所有权协调 | 杀进程后从已提交边界继续；过期Worker不能写回任务或推进有效图状态 |
| 4. 有限多Agent实验 | 主调查Agent动态委派最多两个假设调查子图，隔离上下文并返回结构化证据提案 | fan-out/fan-in、部分失败、父级取消、共享预算与冲突合并有实测；是否提高效果单独评测 |
| 5. 人工审批与处置 | interrupt等待审批，绑定动作版本/目标/参数，执行前重验；动作幂等记录与独立恢复检查 | 重复提交/恢复不会重复执行已确认动作；执行成功与业务恢复分别判断 |
| 6. 演示与交付 | 最小调查工作台、事件时间线、证据引用、恢复/审批演示，完整实验包 | 可复现演示与诚实的效果/费用/可靠性数据，清晰归属框架与项目实现 |

评测贯穿各阶段，不等最后再补。阶段2与3可以交替推进；阶段4必须有稳定单Agent及适合分解的场景。旧手写循环在迁移期冻结为回归参考，新功能验证后逐步转移到图，避免长期维护两套完整实现。固定规则始终保留为业务基线。

## 多Agent的具体任务

优先采用“主调查Agent + 按竞争假设委派的调查子Agent”。例如订单错误率与延迟同时升高时，一条分支检查下游变慢，另一条检查客户端池竞争或配置回归。主Agent根据现有证据决定是否委派；简单任务直接完成。仅在数据来源和工具确实差异明显时，再演进为拓扑/链路与配置/变更专家，不为角色名称建立额外Agent。

子任务输入明确调查问题、范围、已知证据、允许工具和预算；输出假设、支持与反证引用、未知项、已执行查询及消耗。子Agent不能直接覆盖主假设账本或批准处置。主Agent通过统一校验接受提案，遇到冲突追加可区分解释的查询或保留不确定性；不使用多数投票代替证据验证，同模型多个输出也不视为独立真值。

工程重点：子任务与父任务关联；去重查询带数据时效范围；预算分配与回收；分支超时/取消；部分完成的合并；分支检查点命名空间与版本；聚合时去重证据和追踪来源。并发前预分配调用额度，响应后按实际token核算，未知用量不视为零；供应商最终用量未知，不能承诺严格费用硬上限。

首版不做任意递归生成Agent，不上多个编排框架，也不把确定性校验器包装成LLM审判。可选反证审查Agent是后续消融变量，不与首版并行分支一起加入。

## 支撑Agent判断的场景

现有双服务、有限Trace证据适合回归，却不足以证明复杂协作的必要性。优先让相似症状对应不同机制，而非单纯增加服务数量：

- 同样表现为慢请求，区分下游耗时、客户端排队和数据缺失；同时分析成功与失败样本。
- 增加一个真实依赖与受限观测，例如数据库慢查询/锁等待；根据选定故障补对应工具，不先铺满监控组件。
- 加入无关部署、局部故障、多个候选原因与复合异常；采样缺失时允许合理拒答。
- 引入有版本与来源的运行手册或服务依赖资料，评估它是否改变查询选择或处置建议；文档中的指令不能扩大工具权限。

快照比较需要冻结每类工具的数据视图或记录查询结果，不能仅冻结Trace而让其他策略读取不同时间的实时配置。场景真值、注入开关与答案不进入调查上下文。

## 对照与准入

第一组比较规则、普通ReAct和迁移后的单Agent；第二组比较单Agent、顺序委派和并行委派。使用相同模型配置、证据权限和样本集合；同时报告相同总调用/token额度下的结果，以及不同预算下的质量/耗时/成本变化。多Agent额度是父子总和，不给每个分支一整套单Agent预算后宣称公平。

报告诊断正确率、无故障误报、正确拒答、引用关联与抽查语义、协议失败率、重复查询、累计token、端到端耗时、恢复重复调用与独立业务恢复。多Agent还报告委派是否必要、分支重复劳动、冲突处理与分支失败后的行为。多次模型回放与独立环境样本分别计数，保留失败，不补跑替换。

每轮预先固定场景、参数范围、重复次数和预算；开发样本与留出样本分开。复杂策略只有在目标任务上展示可解释收益时才进入默认路径；无收益时保留实验结论和单Agent回退，也属于有效交付。未预设必须获得正向结论或准确率提升。

## 技术选型与边界

主线：Python、LangGraph、Pydantic、FastAPI、PostgreSQL、OpenTelemetry/Jaeger、Docker Compose、自建场景与评测运行器。PostgreSQL任务表负责执行归属，checkpointer负责图进度，两者不是同一事务，不能因引入框架假定已具备所有权隔离。

按需求增加：Prometheus等指标源；运行手册检索（先验证检索必要性，再考虑pgvector）；MCP仅用于稳定工具跨客户端复用或外部工具接入。先在进程内运行子图，只有隔离/扩容需求明确时再考虑独立子Agent进程。LangSmith等远程追踪需另行决定数据与费用边界，本地可观测性可先满足需求。
