# Agent 能力演进路线

## 2026-11-17 当前执行计划

本节覆盖下方历史记录的“下一步”与阶段顺序。主线为结论级证据验证，主动查询增益暂停，多Agent仅做条件准入，暂不推进第二拓扑、平台或后端扩展。按独立可验收问题推进，不以三个机制全部实现为交付前提。

### 亮点一：保留审计成果

真实顺序是先进行实现与模型对照，未观察到查询收益，再穷举审计确认现有开发样本、工具和成功协议下fixed已达最短路径；不能改写为一开始就先做上界审计，也不能推断语义解释质量已饱和。见[审计](../experiments/active-query-comparison.md)。

### 亮点二：主张与证据核对

| 小里程碑 | 交付与准入 | 停止条件 |
| --- | --- | --- |
| A. 真实错误复现 | 找到历史引用/类别验收通过但解释错误的报告；从原始证据重算，保留原文、输入哈希及正确对照 | 找不到实例则交付审计，不先建验证器 |
| B. 最小确定性验证 | 对明确结构化的统计主张检查指标、样本范围、聚合方法及引用作用域，输出支持/矛盾/证据不足；接入现有active主线 | 错误必须被识别，正确对照须保留；人工拆解仅证明结构化主张验证，不冒称自由文本端到端能力 |
| C. 冻结对照 | 在正式入口`evals/run_active_comparison.py`扩展既有结果，比较引用检查与确定性验证；冻结样本、规则、标签和成本 | 结果无收益则保留简单方案与失败，不调验收样本追正结果 |
| D. 条件扩展 | 只有确定性方案仍遗漏真实语义错误才增加语义验证；一次有界修正另作消融 | 复杂方案没有新增拦错价值或误拒/成本不可接受则停止；最多两轮冻结效果对照 |

A已完成一个定向P95单例，见[结果](../experiments/bundle-comparison.md#2026-11-17-结论验证准入审计)。这不是独立验收集或语义错误发生率。B已完成active执行器只读统计验证接口与合成冻结快照机制验收，见[接口与边界](035-query-policy-adapters.md#2026-11-17-结构化统计主张验证独立只读接口)；尚无自由文本提取或发布拦截。下一步进入C的候选主张/独立标签冻结及正式入口配对对照，不顺带增加通用LLM裁判或多轮补查。

三种数据分开记录：历史真实错误、人工变体/正确对照、后续自然模型输出；按原始采集分组，多个改写不算独立样本。报告错误放行、正确主张误拒、有效回答覆盖、修正得失与额外成本的计数/分母，同时注明采集数、报告数和主张数。没有适当抽样依据时不推断总体准确率。

标签来自原始证据重算及人工复核；当前单例仅代码重算与原文核对，未有独立人工二次标注。运行时验证器不能当最终真值，规则生成的诊断也不能当模型诊断成绩。未知或无法证明的因果主张应保留不确定性。自然语言提取阶段若尚未验证，必须明确作用范围。

借鉴[Ragas Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)拆原子主张并逐条检查支持关系的思路，增加本项目统计与作用域约束；当前仅参考文档，尚未采用源码或引入依赖。采用代码前固定commit并检查许可证。语义验证需用独立标签校准，不能以模型自评分数证明效果。

2026-11-17阶段C首轮已完成构造主张开发对照，见[54条主张的结果与限制](../experiments/active-query-comparison.md#2026-11-17-结构化统计主张首轮冻结对照)。自然报告审计发现的近似误拒和告警来源缺口已由v2修复，同开发样本人工提取回放保留11/11条正确主张、拦截1/1条错误，另1条不等式未支持；旧误拒结果保留。见[v2回放及边界](../experiments/bundle-comparison.md#v2修复回放近似表达和告警归属)。下一步定义主张提取与原文绑定验收，再决定自动流程接入，不立即进入语义验证或多Agent。

### 亮点三：仅做准入判断

亮点二最小对照完成后，再投入最多2—3个有效工作日；不是必须花满。先找强单Agent在全部工具、明确竞争解释要求下可重复的实质遗漏，再检查人工分解是否产生互补证据，并与同预算自检/亮点二验证器比较。查询数饱和不能推出解释质量饱和，也不预设闸门失败。

没有证据支持协作需求则结论为“当前未发现引入协作的充分理由”，不实现框架。通过后才考虑双分支、共享证据、查询去重、全局预算及一次证据仲裁，同总预算比较单Agent、顺序委派、并行委派；最多两轮冻结效果对照。只降低耗时就只报告执行收益，不宣称诊断改善。

参考[AutoGen Multi-Agent Debate](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/multi-agent-debate.html)独立分析与消息交换流程，计划用证据仲裁替代示例的多数投票；当前未实现或采用源码。未实现前不将多Agent、语义验证或第二拓扑列为既有能力。

## 多Agent的具体任务

优先采用“主调查Agent + 按竞争假设委派的调查子Agent”。例如订单错误率与延迟同时升高时，一条分支检查下游变慢，另一条检查客户端池竞争或配置回归。主Agent根据现有证据决定是否委派；简单任务直接完成。仅在数据来源和工具确实差异明显时，再演进为拓扑/链路与配置/变更专家，不为角色名称建立额外Agent。

子任务输入明确调查问题、范围、已知证据、允许工具和预算；输出假设、支持与反证引用、未知项、已执行查询及消耗。子Agent不能直接覆盖主假设账本或批准处置。主Agent通过统一校验接受提案，遇到冲突追加可区分解释的查询或保留不确定性；不使用多数投票代替证据验证，同模型多个输出也不视为独立真值。

工程重点：子任务与父任务关联；去重查询带数据时效范围；预算分配与回收；分支超时/取消；部分完成的合并；分支检查点命名空间与版本；聚合时去重证据和追踪来源。并发前预分配调用额度，响应后按实际token核算，未知用量不视为零；供应商最终用量未知，不能承诺严格费用硬上限。

首版不做任意递归生成Agent，不上多个编排框架，也不把确定性校验器包装成LLM审判。可选反证审查Agent是后续消融变量，不与首版并行分支一起加入。

## 支撑Agent判断的场景

现有双服务、有限Trace证据适合回归，却不足以证明复杂协作的必要性。优先让相似症状对应不同机制，而非单纯增加服务数量：

- 同样表现为慢请求，区分下游耗时、客户端排队和数据缺失；同时分析成功与失败样本。
- 增加一个真实依赖与受限观测，例如数据库慢查询/锁等待；根据选定故障补对应工具，不先铺满监控组件。
- 加入无关部署、局部故障、多个候选原因与复合异常；采样缺失时允许合理拒答。
- 引入有版本与来源的运行手册或服务依赖资料，评估它是否改变查询选择或处置建议；文档中的指令不能扩大工具权限。

快照比较需要冻结每类工具的数据视图或记录查询结果，不能仅冻结Trace而让其他策略读取不同时间的实时配置。场景真值、注入开关与答案不进入调查上下文。

## 对照与准入

第一组比较规则、普通ReAct和迁移后的单Agent；第二组比较单Agent、顺序委派和并行委派。使用相同模型配置、证据权限和样本集合；同时报告相同总调用/token额度下的结果，以及不同预算下的质量/耗时/成本变化。多Agent额度是父子总和，不给每个分支一整套单Agent预算后宣称公平。

报告诊断正确率、无故障误报、正确拒答、引用关联与抽查语义、协议失败率、重复查询、累计token、端到端耗时、恢复重复调用与独立业务恢复。多Agent还报告委派是否必要、分支重复劳动、冲突处理与分支失败后的行为。多次模型回放与独立环境样本分别计数，保留失败，不补跑替换。

每轮预先固定场景、参数范围、重复次数和预算；开发样本与留出样本分开。复杂策略只有在目标任务上展示可解释收益时才进入默认路径；无收益时保留实验结论和单Agent回退，也属于有效交付。未预设必须获得正向结论或准确率提升。

## 技术选型与边界

主线：Python、LangGraph、Pydantic、FastAPI、PostgreSQL、OpenTelemetry/Jaeger、Docker Compose、自建场景与评测运行器。PostgreSQL任务表负责执行归属，checkpointer负责图进度，两者不是同一事务，不能因引入框架假定已具备所有权隔离。

按需求增加：Prometheus等指标源；运行手册检索（先验证检索必要性，再考虑pgvector）；MCP仅用于稳定工具跨客户端复用或外部工具接入。先在进程内运行子图，只有隔离/扩容需求明确时再考虑独立子Agent进程。LangSmith等远程追踪需另行决定数据与费用边界，本地可观测性可先满足需求。
