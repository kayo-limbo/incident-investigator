# 同工具、同停止协议的查询策略适配

## 2026-11-18 主张如何进入报告正文（验收约定）

候选主张须保留原文、来源、指标、窗口、统计对象、单位、原精度和已查询引用。两组共用候选顺序、证据、预算和渲染器。引用组仅检查是否已取得该引用；统计组对同一候选再做证据核验。渲染器只呈现该组接纳的内容，避免另一次自由生成改变数值或重新引入已拒绝的判断。

| 核验结果 | 读者看到什么 | 审计保留什么 |
| --- | --- | --- |
| 支持 | 按原精度写入正文，标明采样窗口或“告警记录”。 | 候选、引用、核对值与作用域。 |
| 矛盾 | 省去该断言。若它是应报告项的唯一依据，正文标明该项尚待确认。 | 原断言、矛盾理由及对应观测。核对值不会自动成为模型的新结论。 |
| 证据不足或无法绑定 | 对应报告项写明缺哪一项观测、哪一个判断无法确认。 | 分别记录证据缺口或表达未覆盖，单列计数。 |

两个开发例来自同一慢下游采集。已查询订单样本 P95 为 362.079 ms，候选“订单 P95 约 362.08 ms”获支持时，正文写“事件窗口采样订单 P95 约 362.08 ms”。若来源是告警，正文须写“事件告警记录……”并使用告警实际记录的指标。另一候选“库存 P95 为 352.213 ms”引用了最慢订单的库存耗时；样本库存 P95 独立排序为 352.727 ms。统计组仅在审计中保存错误断言；没有其他已支持的库存 P95 候选时，正文写“本报告尚无法确认库存 P95”。两个示例用于约定行为，当前发布路径尚未接入。

正文对照以采集为组，先冻结应报告项，再用原始观测独立评分。两组各报错误进入正文数/错误总数、正确结论被删数/正确总数、重要结论保留数/应报告总数及额外模型、工具调用数。分母为空时记录不适用。

## 2026-11-17 主张原文绑定v1（受限独立句）

新增`claim_verification.verify_bound_claim(binding, report_text=..., snapshot_id=..., evidence=...)`，调用方提供可信报告原文与已查询证据。`ClaimBinding`包含报告UTF-8 SHA256、Python字符偏移`start/end`（左闭右开，不是字节/UTF-16偏移）、原文`quote`和`StatisticalClaim`。先检查原文哈希、位置与片段完全相等，再核对文本字段，最后调用v2证据验证；不修改调查状态，不执行额外查询。哈希用于版本绑定，不是签名或对恶意调用方的权限隔离。

首版仅支持独立句的受控表达：`事件窗口采样/参考窗口采样/事件告警记录` + `订单/库存/发送前/客户端` + `P95` + `为/=/约` + 数字 + `ms`，可带句号。指标与窗口从原文推导，告警/样本决定statistic、population和method；数值与单位必须一致，“约”及小数位不能增删或改变。不支持省略范围、承接上文、单请求、否定、条件、比较或不等式。完整句边界检查禁止从“并非/如果/假设：……”中截取肯定片段；不分析跨句语义或整篇论证，也不验证报告是否漏报其他主张。

成功绑定返回`binding_status=bound`并附v2的`verification`，其中数值仍可能被判矛盾。哈希/片段不一致、字段不符或表达未支持返回`binding_status=unverified`、原因和`verification=null`；未核验不能当作矛盾、正确拒答或已拦错。非法结构继续抛校验错误。旧`verify_claim`仍是人工结构化接口，不能绕开绑定后宣称检查过原文；当前未接自动发布拦截。

17项执行器专项和36项active主线回归通过，含冻结快照→查询→绑定→证据验证、指标/窗口/数值/来源/精度篡改、哈希/位置错误、否定截断、真实错误值和告警归属。对旧13条人工片段进行不改写适用性检查，绑定0/13、未核验13/13，详情见[覆盖边界](../experiments/bundle-comparison.md#原文绑定v1适用性检查)。这是新输出契约的工程验收，不是自然报告拦错成绩；不继续为这13条句式追加特例。

## 2026-11-17 统计主张v2：近似精度与告警归属

当前验证结果协议升级为`statistical-claim-v2`，调查报告仍为v3且停止条件不变。新增可选`approximation`，必须保留原文中的“约+带1—3位小数的数值+ms”（允许空格），数值必须与`value`一致；由该字面值的小数位确定精度，使用十进制ROUND_HALF_UP核对证据值。无近似标记仍沿用v1三位小数比较，不开放任意容差、整数近似或科学计数法。调用方须保证该片段确实来自原文；Schema仅核对片段与数值的一致性，不能证明提取忠实性，尚无自动提取。

新增`statistic=reported_p95`、`population=alert_record`、`method=reported`组合，只接受已获取的`get_alert`与incident作用域。`metric=client_elapsed_ms`只读取`client_p95_ms`；`orders_ms`只读取显式`orders_p95_ms`，不将客户端耗时冒充服务端订单耗时。允许读取已获取历史告警的`data.alert`封装，但不改旧执行器或推断未知字段。缺少对应指标返回证据不足；参考窗口、未知引用、全量外推和其他指标不构成支持。

告警核验结果`scope=reported_alert_only`，只证明告警记录了该值，不证明Trace充分、全部流量或因果结论。请求/样本结果为`observed_evidence`。例如Trace缺失时仍可核对“告警记录客户端P95约383.7ms”，不可借此支持“采样订单P95为383.7ms”。

16项执行器专项、35项active主线回归通过；覆盖真实舍入误拒、错误库存值仍被拒绝、近似片段不一致/任意容差拒绝、缺Trace告警归属及客户端/服务端指标隔离。开发回放见[自然报告修复验收](../experiments/bundle-comparison.md#v2修复回放近似表达和告警归属)。旧v1冻结结果保留，必须使用对应归档源码复现；新源码不续跑旧批次。

## 2026-11-17 结构化统计主张验证（独立只读接口）

`ActiveInvestigation.verify_claim(claim)`接入`claim_verification.py`，只读当前调查已获取的证据，返回`statistical-claim-v1`结果：`status`为`supported`、`contradicted`或`insufficient_evidence`，附`reason`、`expected_value`和原主张。不读取私有快照、不调用模型或工具、不修改调查状态/预算，也不改变原v3报告、停止条件与诊断。当前未接模型输出解析、报告发布拦截或正式冻结对照；不能宣称自动拦截自然语言报告。

主张字段：`snapshot_id`、`evidence_id`、`window`（reference/incident）、`metric`（orders_ms/inventory_ms/pre_send_ms）、`statistic`（p95/request_value）、`population`（observed_non_null/request/all_traffic）、`method`（nearest_rank/none）、`value`、`unit=ms`，单请求另需`trace_id`。P95只接受nearest_rank且不能绑定单请求；请求值只接受none及request。错误结构、未知字段、非有限数值直接校验失败，不能由调用方自设容差。

P95依据同窗口已查询摘要的统计值（现有工具按每个指标的非空样本独立nearest-rank计算），单请求值依据已查询的同ID详情；不允许把详情数值当聚合依据。仅在引用与作用域充分时比较数值，按固定小数点后三位毫秒舍入一致性判断；数值错误为矛盾，跨快照/窗口、未查询引用、来源缺失、全量流量主张均为证据不足。验证器信任执行器产生的工具结果，不独立证明工具统计实现或快照真值；评测仍须从原始观测独立重算。

代表调用（已有`run`和事件摘要证据`summary`）：

```python
result = run.verify_claim(dict(
    snapshot_id=run.snapshot_id, evidence_id=summary['id'], window='incident',
    metric='inventory_ms', statistic='p95', population='observed_non_null',
    method='nearest_rank', value=352.727, unit='ms'))
```

人工拆解的历史错误只用于明确机制需求，新增验收使用20请求合成冻结快照，让订单P95和库存P95落在不同请求，并包含高于P95的极值。错误库存P95主张被识别，库存/订单P95及单请求正确对照保留；另验证错窗口、错请求、未获取引用、全量外推和缺失来源不被支持，所有校验均保持报告和预算不变。14项执行器专项、32项active主线回归通过（项目虚拟环境运行`python -m unittest discover -s tests -p "test_active*.py" -v`），无模型调用。这是机制测试，不是独立真实模型效果对照。下一步在正式`evals/run_active_comparison.py`冻结候选主张、独立标签及引用检查/统计验证的配对结果，保持开发与验收来源分离。

2026-11-15作用域Schema修订：模型可见查询按tool区分三种结构，摘要要求非空window，下钻要求非空window及32位trace_id，配置/入口比较的window和trace_id只能省略或为null。react直接使用该联合Schema，active在Plan.query内使用；其余计划约束不变。Schema仍通过既有system消息提供，不代表供应商强制约束解码。执行器保留原Query和query_key独立校验，因此忽略Schema的动作仍以invalid_query_scope拒绝并保留有界候选诊断及真实用量，不自动补窗口或重试。报告仍为v3；提示Schema变化会改变冻结源码哈希，新模型实验须新建批次，旧失败不改写。本次仅离线及模拟HTTP验证，没有新模型效果数据。

## 2026-11-14 混合阶段的局部定位（v3，当前协议）

窗口内各阶段P95独立计算，`mixed`不代表同一请求同时出现库存慢和发送前等待。v3在正常参考窗口、事件摘要为mixed时增加一个明确任务：定位事件摘要`drilldown_ids[0]`（按订单耗时降序的最慢采样请求）。下钻结果写入`state.localization`，包含请求ID、单请求阶段、缺口及摘要/详情引用；不能替代窗口统计，也不能推断其他请求或总体的联合分布。阈值沿用阶段规则，不作因果推断。

只有这个目标请求的下钻能消除局部缺口并参与候选评分，其他已发现请求仍可查询但不会补齐该缺口。下钻数据字段缺失时保留缺口；本应充分的变化分类在定位尚未完成时继续调查，预算不足则拒答。缺失来源或不满足变化条件的调查不强行追加下钻。原假设状态描述窗口变化特征，不用单请求覆盖假设的支持/反证；局部结论单列。

固定策略保留四项原有顺序，仍需局部定位时执行同一下钻；react/active可在发现目标后自行安排顺序。去评分版本也包含该候选。正式入口逐步检查固定策略动作并重建局部定位，评分输出保留局部结果。协议标记为`active-query-policies-v3`与`active-reference-v3`，旧报告需旧冻结源码复核。

这是新增的报告充分性要求，mixed任务可能多花一次查询，不能与v2直接比较查询成本或宣称效率改善。原有真实开发视图未触发该要求；合成快照只验证窗口与单请求阶段的区分、错误请求不补齐缺口、预算拒答、同权限及报告篡改检测。

## 2026-11-13 分类充分性修订（v2）

新报告使用`active-query-policies-v2`（参考执行器为`active-reference-v2`）。假设按各自证据需求逐步更新：下游变化需两个有效摘要，容量与入口特征分别需对应比较。`missing`保留未查询或来源不可用的缺口，历史`resolved_gaps`仅记录实际补齐的证据需求；候选评分改为该查询能覆盖的缺口数，仍是启发式，不是信息增益模型。

`state.sufficiency`分开记录事件阶段是否可定位、参考窗口是否有效、分类是否充分、未核查因素及是否检查完全部因素。正常参考、明确事件阶段、至少两种已支持变化即可停止为`competing_changes`，范围为`multiple_changes_exist`。未查的第三因素保持open和missing；`exhaustive=false`，不得解释为已列出全部复合因素。单一变化分类仍要求配置及入口比较齐全，保留原阈值；无异常结论仍只描述采样症状，不排除无症状的配置变化。来源缺失、异常参考及预算不足继续保守拒答。

固定、react、active共享此停止条件，固定查询顺序不变。单请求下钻仍不能补齐当前窗口级变化证据，因此不加入评分候选。正式对照入口的评分输出携带同一充分性信息，逐步重放校验状态和缺口消除记录。旧批次须用原冻结源码复核；新语义须重新冻结，不能续跑旧批次。此次无付费模型调用。

## 三种策略

| 策略 | 决策输入与动作 | 共同边界 |
| --- | --- | --- |
| fixed | 固定顺序：参考摘要、事件摘要、配置比较、入口比较 | 同一工具、证据与自动停止规则；健康或来源缺失可提前停 |
| react | 已观测证据、工具预算、工具结果枚举；输出Query | 不给假设状态或评分候选，允许已发现请求下钻 |
| active | 同上，加程序假设状态及候选建议；输出Plan | 校验假设ID、gap、预期分支；评分仅建议，不强制最高分 |

普通策略由执行器补足兼容Plan，报告标记`plan_origin=executor_from_query`，不冒充模型规划。主动策略记录model来源，固定策略记录fixed_policy。所有结论来自共同状态机，不把模型查询动作当作诊断成功。

`--no-scoring`仅用于active：移除分数并恢复固定候选顺序，保留假设、候选及计划校验。这是“分数展示与排序”的有限消融，不是完全移除主动规划；完整的去规划消融尚未实现。固定流程不主动下钻单请求，其他两种有相同工具权限可选择下钻。

## 预算与失败

默认含告警6次工具预算，最多5次模型决策（budget−1），120秒总期限和40000累计token停止阈值。调用账本保留模型失败/超时/取消及未知用量；响应后检查token，达到阈值或用量未知时不执行候选动作。最后一次响应可能超额，不是费用硬上限。

非法Schema、预期分支、重复查询等直接结束，不自动重试；动作不进入已接纳调查历史。模型错误保留已有白名单原因码，不保存供应商原文。报告分别记录执行termination与领域state.stop，执行completed可能对应证据不足，不等于诊断正确。

库层取消抛出携带部分报告的PolicyCancelled；CLI保存部分报告并返回130。模型传输使用async with关闭资源。无Worker持久化恢复、纠错或并行执行；快照读取失败仍由调用方处理，CLI可能留下空目标文件，重试需新路径。

## 使用

默认fixed不读取密钥、不访问模型。输出独占创建，不覆盖已有报告：

```powershell
python -m backend.investigation.active_cli SNAPSHOT_SHA256 --store .snapshots/paired-20261109-development-v1/snapshots --output .snapshots/NEW_POLICY.private.json
python -m unittest discover -s tests -p 'test_active_policies.py' -v
```

显式`--strategy react`或`active`才读取既有ModelConfig配置并调用API，会外发受限观测并产生费用；本轮没有执行。单快照CLI不判定数据集split，保留集纪律需由后续冻结批量评测入口保证，不把本地文件接口宣称为隔离边界。
